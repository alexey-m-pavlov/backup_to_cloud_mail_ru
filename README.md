# Backup-ToCloudMailRu

Автоматизированное резервное копирование набора локальных папок в облако
**Cloud@mail.ru** через rclone. Реализовано на PowerShell 7, запускается
из Планировщика задач Windows 11.

## Возможности

- Рекурсивное копирование произвольного набора локальных папок в облако.
- Режимы `copy` (безопасный, без удаления на удалённой стороне) и `sync`.
- Защита от параллельных запусков через lock-файл.
- Пароль конфигурации rclone читается из Windows Credential Manager.
- Предварительная проверка файлов, превышающих лимит облака.
- Раздельный лог неудачных файлов (`failed_YYYYMMDD.log`).
- Режим `-WhatIf` для безопасной проверки без реальных операций.
- Единый лог-файл на сутки, ротация по сроку хранения.
- Логирование через `StreamWriter` с буферизацией.
- Маски исключений для каждой папки.
- Кэш хэшей локальных файлов через `local-hasher`: повторные запуски
  проходят быстрее за счёт того, что rclone не перечитывает неизменённые
  файлы с диска.
- Работа в фоновом режиме без появления окна консоли (см. раздел
  «Запуск из Планировщика задач»).
- Встроенный обходной путь для ошибок `400 Bad Request` через квирк
  `retry400` (см. раздел «Решение проблем с ошибками 400»).

## Требования

- **Windows 11** (также работает на Windows 10).
- **PowerShell 7+** (`pwsh.exe`).
- **rclone** — скачать с [rclone.org](https://rclone.org/downloads/).
- **Модуль TUN.CredentialManager**:
  ```powershell
  Install-Module -Name TUN.CredentialManager -Scope CurrentUser -Force
  ```
- Действующий аккаунт **Cloud@mail.ru** и пароль приложения Mail.ru.

## Разовая настройка

### 1. Создание структуры папок

```
backup_to_cloud_mail_ru/
├── secrets/
└── logs/
```

Папки создаются автоматически при первом запуске скрипта, но `secrets/`
удобнее создать заранее — туда вы положите `rclone.conf`.

### 2. Настройка rclone для Cloud@mail.ru

Создайте пароль для внешних приложений в настройках безопасности Mail.ru.
Выберите уровень доступа **«Полный доступ к Почте, Облаку и Календарю»**
(all protocols) — вариант «Только Cloud (WebDav)» с rclone не работает.

Укажите rclone, где хранить конфиг. Два способа:

**Способ A — через переменную окружения** (действует только в текущей
сессии PowerShell):

```powershell
$env:RCLONE_CONFIG = "C:\Scripts\backup_to_cloud_mail_ru\secrets\rclone.conf"
rclone config
```

**Способ B — через параметр `--config`** при каждом вызове:

```powershell
rclone --config "C:\Scripts\backup_to_cloud_mail_ru\secrets\rclone.conf" config
```

В диалоге `rclone config`:

- `n` — новый remote
- Имя: `mailru`
- Тип: **`mailru`** (не `webdav`)
- Введите email и пароль приложения

Проверьте подключение:

```powershell
rclone --config "C:\Scripts\backup_to_cloud_mail_ru\secrets\rclone.conf" lsd mailru:
```

### 3. Добавление hasher-remote для локальных файлов

После того как remote `mailru` создан, добавьте в `rclone.conf` секцию
`local-hasher` — обёртку над локальной файловой системой, которая
кэширует хэши локальных файлов. Откройте конфиг:

```powershell
rclone --config "C:\Scripts\backup_to_cloud_mail_ru\secrets\rclone.conf" config
```

Выберите `n` (новый remote) и создайте:

- Имя: `local-hasher`
- Тип: `hasher`
- `remote`: оставить **пустым** (Enter)
- `hashes`: `mailru`
- `max_age`: `off`

В итоге `rclone.conf` должен выглядеть так:

```ini
[mailru]
type = mailru
user = ваш_логин@mail.ru
pass = <обфусцированный пароль>
token = <токен>
quirks = retry400

[local-hasher]
type = hasher
remote =
hashes = mailru
max_age = off
```

**Почему именно так:**

- `remote =` (пустое) означает «локальная файловая система». Hasher будет
  кэшировать хэши любых локальных путей, которые ему передадут.
- `hashes = mailru` — модифицированный SHA1, который использует Mail.ru.
  Другие типы хэшей в этой схеме не нужны.
- `quirks = retry400` — обходной путь для известной проблемы бэкенда
  Mail.ru: массовых ошибок `400 Bad Request` при чтении каталогов. rclone
  будет автоматически повторять такие запросы. Подробнее — в разделе
  «Решение проблем с ошибками 400».
- Имя `local-hasher` **жёстко зашито в скрипте**. Если переименуете секцию —
  поправьте переменную `$localHasherRemote` в блоке 2 скрипта.

### 4. Шифрование конфигурации rclone

```powershell
rclone --config "C:\Scripts\backup_to_cloud_mail_ru\secrets\rclone.conf" config
```

Выберите `s` (Set configuration password) и задайте пароль. Запомните его —
он понадобится на следующем шаге.

### 5. Сохранение пароля конфигурации в Credential Manager

От имени того же пользователя, под которым будет работать задача:

```powershell
Import-Module TUN.CredentialManager
$cred = Get-Credential -Message "Пароль конфигурации rclone" -UserName "rclone"
New-StoredCredential -Target "rclone-config-pass" -Credential $cred -Persist LocalMachine
```

Имя цели (`rclone-config-pass`) должно совпадать с полем `CredentialTarget`
в `backup.config.json`.

Если при выполнении `New-StoredCredential` возникает ошибка
`Could not load type 'System.Web.Security.Membership'`, в системе
установлен старый модуль `CredentialManager`. Удалите его и установите
форк:

```powershell
Uninstall-Module -Name CredentialManager -AllVersions -Force
Install-Module -Name TUN.CredentialManager -Scope CurrentUser -Force
```

### 6. Проверка связки

```powershell
$env:RCLONE_CONFIG_PASS = (Get-StoredCredential -Target "rclone-config-pass").GetNetworkCredential().Password
rclone --config "C:\Scripts\backup_to_cloud_mail_ru\secrets\rclone.conf" lsd mailru:
$env:RCLONE_CONFIG_PASS = $null
```

Если команда вывела список папок — всё настроено.

### 7. Пробный запуск

```powershell
.\Backup-ToCloudMailRu.ps1 -WhatIf
```

Скрипт покажет, какие операции были бы выполнены, без реальной загрузки.

## Кэширование хэшей

Ключевая особенность текущей схемы — **кэш хэшей локальных файлов** в
`local-hasher`. Он ускоряет повторные запуски за счёт того, что rclone
не перечитывает файлы, не изменившиеся с прошлого раза.

### Как это работает

1. Первый запуск: rclone обходит локальные папки, вычисляет хэши типа
   `mailru` для каждого файла и **сохраняет их в локальную базу данных**.
   Это долгий этап — файлы реально читаются с диска.
2. Последующие запуски: для каждого файла rclone сравнивает размер и
   mtime с записью в кэше. Если они совпадают — берёт хэш из кэша, **не
   читая файл**. Если файл изменился — перечитывает и обновляет кэш.
3. Сравнение с облаком идёт по размеру и mtime (см. «Известные
   ограничения»), но **локальная сторона** уже не читается лишний раз.

### Где хранится кэш

База данных `local-hasher` лежит в кэш-директории rclone:

```
%LOCALAPPDATA%\rclone\kv\local-hasher.bolt
```

Точный путь можно узнать командой:

```powershell
rclone config paths
```

При первом запуске на большой папке файл `.bolt` может вырасти до сотен
мегабайт — это нормально. **Не удаляйте его**, иначе следующий запуск
снова будет долгим.

### Как обновить кэш вручную

Если нужно принудительно пересчитать все хэши (например, после переноса
на новую машину или при подозрении на порчу кэша), используйте `hashsum`
с флагом `--download`:

```powershell
rclone hashsum mailru --download "local-hasher:D:\Energames"
rclone hashsum mailru --download "local-hasher:D:\Users\pavlov\Pictures\Фотографии"
```

Подставьте свои пути из `Folders[].LocalPath`. Команда перечитает каждый
файл, обновит кэш и выведет список хэшей.

### Сброс кэша

Полностью очистить кэш:

```powershell
rclone backend drop local-hasher:
```

После этого следующий запуск будет таким же долгим, как первый.

## Конфигурация

### Корневые поля

| Поле | Обязательное | Описание |
|---|---|---|
| `RclonePath` | Да | Полный путь к `rclone.exe` |
| `RcloneConfigPath` | Нет | Путь к `rclone.conf`. Относительный — от папки скрипта |
| `RemoteName` | Да | Имя remote для облака (обычно `mailru`) |
| `TransferMode` | Нет | `copy` (по умолчанию) или `sync` |
| `ExtraFlags` | Нет | Массив дополнительных флагов rclone |
| `MaxFileSizeBytes` | Нет | Лимит размера файла. По умолчанию 2 ГБ |
| `CredentialTarget` | Да | Имя учётной записи в Credential Manager |

### Раздел `Retry`

| Поле | Описание |
|---|---|
| `MaxRetries` | Максимальное число попыток на папку |
| `BaseDelaySeconds` | База экспоненциальной задержки между попытками |

### Раздел `Logging`

| Поле | Описание |
|---|---|
| `Directory` | Папка логов. Относительный путь — от папки скрипта |
| `RetentionDays` | Сколько дней хранить логи. `0` — не удалять |

### Раздел `Folders`

| Поле | Обязательное | Описание |
|---|---|---|
| `Enabled` | Нет | `false` — запись пропускается |
| `LocalPath` | Да | Абсолютный путь к локальной папке |
| `RemotePath` | Да | Путь на WebDAV-хранилище |
| `ExcludeMask` | Нет | Маски исключений через `;` (синтаксис rclone) |

### Режимы передачи

- **`copy`** — только добавляет новые и изменённые файлы. Удалённые локально
  файлы **остаются** в облаке. Безопасный режим, рекомендуется по умолчанию.
- **`sync`** — делает удалённую папку точной копией локальной, **удаляя**
  всё лишнее на удалённой стороне.

### Полезные флаги в `ExtraFlags`

- `--transfers N` — число параллельных передач. Для множества мелких файлов
  можно поднять с 4 до 8–16. По умолчанию в скрипте стоит `8`.
- `--tpslimit N` — ограничение числа запросов в секунду. Пригодится, если
  Mail.ru начнёт возвращать ошибки `429 (Too Many Requests)`.
- `--fast-list` — получить список файлов одним запросом вместо обхода
  директорий по одной. Ускоряет фазу сканирования.
- `--stats 10s` — как часто rclone печатает строку прогресса. По умолчанию
  раз в минуту; `10s` делает вывод заметно «живее».

### Чего в `ExtraFlags` быть не должно

- **`--checksum`** — для текущей схемы не нужен. Mail.ru не отдаёт
  серверные хэши, поэтому сравнение с облаком всё равно идёт по размеру и
  mtime. Флаг только заставляет hasher вычислять локальные хэши, которые
  не с чем сопоставить.

## Особенность путей в JSON

JSON использует обратный слэш (`\`) как служебный символ экранирования.
В полях с **локальными путями** бэкслэши нужно **удваивать**:

| Что вы хотите | Что писать в JSON |
|---|---|
| `C:\Tools\rclone\rclone.exe` | `"C:\\Tools\\rclone\\rclone.exe"` |
| `D:\ImportantData\Documents` | `"D:\\ImportantData\\Documents"` |
| `\\server\share\folder` (UNC) | `"\\\\server\\share\\folder"` |
| `logs` (относительный) | `"logs"` — без изменений |
| `secrets\rclone.conf` (относительный) | `"secrets\\rclone.conf"` |

Правило применяется к полям:

- `RclonePath`
- `RcloneConfigPath`
- `Logging.Directory`
- `Folders[].LocalPath`

**Поле `Folders[].RemotePath` — исключение.** Это путь на WebDAV-сервере,
rclone требует там **прямые слэши**: `"/Backup/Documents"`.

**Относительные пути** в `RcloneConfigPath` и `Logging.Directory`
разрешаются **от папки скрипта** (`$PSScriptRoot`), а не от рабочей папки
процесса.

## Запуск из Планировщика задач

Скрипт работает в фоне, без появления окна консоли. Это достигается за
счёт режима задачи **«Выполнять независимо от того, выполнен ли вход
пользователя в систему»** — задача запускается в неинтерактивной сессии,
где окно просто не создаётся.

### Пошаговая настройка

1. Откройте **Планировщик задач** → **Создать задачу** (не «простую»,
   а именно задачу, чтобы получить доступ ко всем настройкам).

2. Вкладка **«Общие»**:
   - **Имя**: `Backup-ToCloudMailRu`.
   - **Параметры безопасности**: выберите **«Выполнять независимо от
     того, выполнен ли вход пользователя в систему»**.
   - **«Выполнять с наивысшими правами»** — включите, если нужен доступ
     к защищённым папкам.
   - Нажмите **ОК** — Планировщик запросит пароль пользователя. Введите
     пароль от учётной записи Windows. Того же самого пользователя,
     который сохранил пароль rclone в Credential Manager на шаге 5
     разовой настройки.

3. Вкладка **«Триггеры»** → **Создать**:
   - Запуск по расписанию (например, ежедневно в 03:00).
   - Если задача может выполняться дольше суток, включите
     «Повторять задачу каждые: 1 день» в дополнительных настройках.

4. Вкладка **«Действия»** → **Создать**:
   - **Программа/скрипт**: `pwsh.exe`
   - **Аргументы**:
     ```
     -NoProfile -ExecutionPolicy Bypass -File "C:\Scripts\backup_to_cloud_mail_ru\Backup-ToCloudMailRu.ps1"
     ```
   - **Рабочая папка**: `C:\Scripts\backup_to_cloud_mail_ru`
     (папка, где лежат `Backup-ToCloudMailRu.ps1` и `backup.config.json`).

5. Вкладка **«Условия»**:
   - Снимите **«Запускать только при питании от электросети»**, если
     задача работает на ноутбуке.
   - Остальные пункты оставьте как есть.

6. Вкладка **«Параметры»**:
   - **«Не запускать новую задачу, если предыдущая ещё выполняется»** —
     включите. Это дополнительная страховка поверх lock-файла в скрипте.
   - **«Остановить задачу, если она выполняется дольше»** — по желанию.
     Если резервное копирование может идти часами, лучше отключить.
   - **«Если задача завершилась с ошибкой, перезапустить»** — можно
     оставить по умолчанию.

### Проверка

- **Правый клик по задаче → «Выполнить»**. Окно консоли не появится.
- Откройте `logs\backup_YYYYMMDD.log` — там будет шапка запуска и вывод
  rclone.
- Откройте журнал задачи в Планировщике: вкладка **«Журнал»** покажет
  время запуска и код возврата (`0x0` — успех, `0x2` — частичный сбой).

### Если задача не запускается

- **Проверьте, что пароль от учётной записи Windows введён правильно.**
  Режим «независимо от входа» требует явного пароля; пустой пароль не
  подойдёт.
- **Проверьте, что задача запускается от того же пользователя**, который
  сохранил `rclone-config-pass` в Credential Manager. Иначе скрипт не
  сможет прочитать пароль конфигурации rclone.
- **Загляните в журнал задачи** — там будет причина отказа, если запуск
  вообще не состоялся.

### Альтернатива для интерактивного режима

Если по каким-то причинам режим «независимо от входа» недоступен, можно
вернуться к опции «Выполнять только при входе пользователя в систему» и
использовать обёртку `wscript.exe` с VBScript для скрытия окна. Но это
лишний файл и хрупкое решение — рекомендуется первый вариант.

## Коды выхода

| Код | Значение |
|---|---|
| `0` | Успех — все включённые папки синхронизированы |
| `1` | Критическая ошибка: конфиг, rclone, remote, учётные данные |
| `2` | Частичный сбой или превышение лимита размера файла |
| `3` | Скрипт уже запущен (сработал lock-файл) |

## Логи

В папке `logs/` ведутся два типа логов, оба — по одному файлу на сутки.

### Основной лог `backup_YYYYMMDD.log`

- Полный ход выполнения: шапка запуска, список папок, вывод rclone,
  ошибки, итоговый статус.
- Кодировка UTF-8 без BOM.
- Уровни: `INFO`, `WARNING`, `ERROR`.
- Буферизация: сброс для `WARNING`/`ERROR` — немедленно, для `INFO` —
  каждые 50 строк и при завершении скрипта.

### Лог неудачных файлов `failed_YYYYMMDD.log`

- Только неудачные файлы.
- Формат строки:
  ```
  [YYYY-MM-DD HH:MM:SS] [LocalPath -> remote:RemotePath] file : сообщение
  ```
- `AutoFlush = $true` — записи сразу пишутся на диск.
- Служебные маркеры `<общая ошибка>`, `<папка>`, `<исключение>` — когда
  конкретный файл не назван.
- Повторные попытки могут дать дубликаты строк по одному файлу.

### Ротация

Файлы обоих типов старше `RetentionDays` (по умолчанию 30) удаляются при
следующем запуске.

## Безопасность

- Пароль конфигурации rclone хранится в **Windows Credential Manager**,
  зашифрован DPAPI и привязан к пользователю и машине.
- Через переменную окружения `RCLONE_CONFIG_PASS` пароль передаётся
  процессу rclone; переменная очищается в `finally`.
- Пароль remote (Mail.ru) хранится внутри `secrets/rclone.conf`, который
  зашифрован паролем конфигурации rclone.
- Трафик к Cloud@mail.ru идёт по HTTPS.
- Lock-файл использует `FileOptions::DeleteOnClose` — ОС удаляет его
  автоматически при завершении процесса.
- Папка `secrets/` исключена из git.
- В режиме «независимо от входа» задача выполняется в фоновой сессии без
  окна консоли и без доступа к интерактивному рабочему столу.

## Перенос между машинами

`secrets/rclone.conf` **можно** копировать между машинами — он защищён
паролем конфигурации.

Пароль конфигурации в Credential Manager перенести **нельзя**: он
зашифрован DPAPI и привязан к пользователю и машине. На новой машине
нужно заново выполнить шаг 5 разовой настройки:

```powershell
Import-Module TUN.CredentialManager
$cred = Get-Credential -Message "Пароль конфигурации rclone" -UserName "rclone"
New-StoredCredential -Target "rclone-config-pass" -Credential $cred -Persist LocalMachine
```

Используйте **тот же** пароль, что и на исходной машине.

Кэш хэшей (`%LOCALAPPDATA%\rclone\kv\local-hasher.bolt`) переносить
**не нужно** — на новой машине он заполнится при первом запуске
автоматически.

При переносе задачи в Планировщике не забудьте **заново ввести пароль
учётной записи Windows** на вкладке «Общие» — привязка к пользователю
тоже локальная.

## Известные ограничения

- **Лимит 2 ГБ на файл** на бесплатном тарифе Cloud@mail.ru. Файлы больше
  лимита логируются как `WARNING` и пропускаются.
- **Первый запуск долгий.** rclone перечитывает все локальные файлы, чтобы
  заполнить кэш хэшей. На больших папках (десятки тысяч файлов) это может
  занять часы. Последующие запуски проходят быстрее за счёт кэша.
- **Mail.ru не отдаёт серверные хэши.** Поэтому `--checksum` в текущей
  схеме не даёт полноценного сравнения по хэшу. rclone сравнивает локальные
  и удалённые файлы по **размеру и mtime**. Если mtime на сервере не
  сохраняется (типичная проблема WebDAV), rclone может периодически
  перезаливать неизменённые файлы. Проверить это можно, сравнив время
  файла на сервере с локальным через `rclone lsl mailru:/путь`.
- **Нет теневого копирования (VSS).** Файлы, открытые другими приложениями,
  могут копироваться в несогласованном состоянии.
- **Одна копия у одного провайдера.** Не соответствует правилу 3-2-1.
- **Данные в облаке не шифруются на клиенте.** HTTPS защищает канал, но не
  сервер. При необходимости используйте `crypt`-remote rclone.
- **Нет уведомлений о сбоях.** Результат доступен через логи и код выхода.
- **Дубликаты в failed-логе при повторных попытках.** Один и тот же файл
  может появляться несколько раз.
- **Фоновый режим не даёт интерактивной отладки.** При запуске из
  Планировщика вы не видите вывод в реальном времени — смотрите лог-файл.
  Для отладки запускайте скрипт вручную из консоли или с `-WhatIf`.

## Решение проблем с ошибками 400

При работе с Cloud@mail.ru через rclone могут возникать массовые ошибки
`HTTP 400 Bad Request` при чтении каталогов. В логе это выглядит так:

```
... error reading destination directory: file error 400 ()
```

Это известная проблема бэкенда Mail.ru, для борьбы с которой в rclone
предусмотрен специальный флаг (quirk) `retry400`. Он заставляет клиент
**повторять запрос** при получении ответа `400`, что часто помогает
обойти временный сбой на стороне сервера[reference:1].

> **Важно:** `quirks` — это низкоуровневые флаги, предназначенные для
> диагностики и обхода проблем бэкенда. Их поведение не гарантируется
> между версиями rclone и может быть изменено или удалено в будущем[reference:2].

### Как включить `retry400`

1. Откройте `secrets\rclone.conf`.
2. Найдите секцию `[mailru]` и добавьте в неё строку `quirks = retry400`:

   ```ini
   [mailru]
   type = mailru
   user = ваш_логин@mail.ru
   pass = <обфусцированный пароль>
   token = <токен>
   quirks = retry400
   ```

3. Сохраните файл. Перезапуск скрипта не требуется — настройка
   подхватится при следующем запуске.

### Что делать, если `retry400` не помог

Если ошибки `400` продолжаются, попробуйте следующие шаги:

- **Проверьте спецсимволы в путях.** В некоторых случаях ошибка `400`
  возникала из-за символа `%` в именах файлов или папок. Просмотрите лог
  и попробуйте переименовать проблемные каталоги, убрав из них
  нестандартные символы.
- **Разбейте задачу на части.** Слишком длинные или сложные пути (как,
  например, `sites/energames.com/.games/.../artworks/title/src`) могут
  провоцировать ошибку. Настройте в `backup.config.json` несколько
  отдельных записей для подпапок вместо одной большой папки.
- **Попробуйте другую версию rclone.** Если ошибки появились после
  обновления, возможно, стоит временно откатиться на предыдущую
  стабильную версию.
